utube-trend-tracer · 시스템 구조

수집은 뒤에서 돌고, 화면은 결과만 읽는다

유튜브 트렌드 서비스를 무료 티어 4개로 조립한 구조. 핵심은 단순한 규칙 하나다 — 무거운 일(API 호출·계산)은 전부 배치에서 끝내고, 사용자가 보는 화면은 완성된 결과만 조회한다.

1. 네 개의 무료 티어

각 레이어는 자기가 제일 잘하는 일만 한다. 어느 하나가 다른 하나의 일을 대신하지 않는다.

UI Vercel Next.js 화면 서빙. 랭킹 보드와 채널 상세를 보여준다.
소스 GitHub 코드 한 곳(모노리포). 공개 리포라 배치 실행이 무료.
DB Supabase Postgres. 수집 원본과 계산된 랭킹을 저장.
배치 GitHub Actions 하루 3회 크론. 수집·분류·점수 계산을 수행.

2. 데이터는 한 방향으로만 흐른다

유튜브에서 데이터를 가져오는 쪽과, 사용자에게 보여주는 쪽이 완전히 분리돼 있다. 두 흐름이 만나는 지점은 Supabase 한 곳뿐이다.

3. 열쇠를 두 개로 나눈 이유

같은 DB를 쓰지만 배치와 웹이 드는 열쇠가 다르다. 브라우저에 나가는 코드에는 읽기만 되는 열쇠를 넣는다.

유튜브 API 키는 한 발 더 나아가, 웹 쪽에 아예 존재하지 않는다. 배치에서만 쓰이므로 GitHub Secrets와 개발자 로컬 파일에만 있고, 브라우저로 전달되는 코드에는 들어갈 경로 자체가 없다.

4. 비용은 0원에서 시작한다

네 서비스 모두 무료 한도 안에서 운영을 시작한다. 한도에 부딪히지 않도록 각각 대응책을 미리 정해뒀다.

서비스무료 한도사용 계획한도 관리
YouTube API일 10,000유닛 일 3,000~7,000 한도 임박 시 수집만 중단 — 화면은 계속 동작
GitHub Actions공개 리포 무제한 일 3회 × 수 분 공개 리포라 실행 시간 과금 없음
Supabase500MB 수십 MB 예상 30일 지난 데이터 자동 삭제 + 추적 채널 2,000개 상한
Vercel개인 사용 무료 정적 화면 + DB 조회 화면에서 계산하지 않으므로 부하가 낮음

5. 이렇게 정한 이유

구조를 고를 때 실제로 걸렸던 문제들과, 그 문제가 어떻게 이 선택으로 이어졌는지.

화면에서 계산하지 않는다 사용자가 페이지를 열 때 트렌드를 계산하려면 유튜브 API를 불러야 하고, 그러면 방문자가 늘수록 쿼터가 타들어 간다. 게다가 API 키가 서버 코드에 노출될 여지가 생긴다. 배치에서 미리 계산해두면 두 문제가 동시에 사라진다.
크론 시각이 아니라 실제 시각으로 계산한다 GitHub Actions의 예약 실행은 상황에 따라 수십 분씩 늦어질 수 있다. "3시에 돌 예정이었으니 8시간이 지났다"고 가정하면 점수가 틀어진다. 그래서 저장된 실제 시각의 차이로 증가 속도를 계산한다 — 늦게 돌아도 점수는 정확하다.
수집이 실패해도 서비스는 죽지 않는다 배치와 서빙이 분리돼 있으니, 수집이 한 번 건너뛰어도 화면은 직전 랭킹을 그대로 보여준다. 다음 주기에 자동으로 따라잡는다.
리포를 공개로 두는 게 이득이다 공개 리포는 Actions 실행 시간이 무제한이라 배치 비용이 0원이 된다. 대신 운영 리포트를 리포에 남길 때 키나 연락처 같은 민감 정보가 섞이지 않도록 규칙을 문서에 명시해뒀다.
오래된 데이터는 계속 지운다 30일이 지난 기록을 자동으로 삭제한다. 무료 DB 용량을 지키는 방법이기도 하지만, 그보다 유튜브 API 약관이 요구하는 사항이다.

6. 지금 어디까지 왔나

설계 문서(SPEC·PLAN) 확정, 환경 연결 검증 완료 · 2026-08-08
Supabase에 테이블 7개를 만들고 접근 규칙이 의도대로 동작하는지 확인했다. 유튜브 API 키도 실제 호출로 검증했다. 다음은 개발 환경 구성을 마치고, 카테고리 분류기부터 만드는 단계다. 화면은 수집이 2주간 쌓인 뒤에 공개한다.
